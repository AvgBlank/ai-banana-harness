- The product is a Rust Cargo workspace at the repository root (`crates/`) plus the desktop app in `gui/` (TypeScript, with its own rules in `gui/AGENTS.md`). Repeatable workflows go through the root `Makefile` (`make setup`, `make run`, `make test`, `make lint`, `make clean`, and the desktop app's `make gui-setup`, `gui-dev`, `gui-build`, `gui-lint`, `gui-test`, `gui-e2e`); add a target when a new workflow is repeatable rather than documenting an ad hoc command.
- Changes MUST pass `make lint` (`cargo fmt --check`, and clippy on all targets with `-D warnings`) and `make test` before they are committed; a change that touches `gui/` or the sidecar also passes `make gui-e2e`. CI runs them on Linux and macOS.
- Crate boundaries: `harness-llm`, `harness-tools`, `harness-mcp` and `harness-store` are leaves that MUST NOT depend on each other and define their own boundary types; `harness-core` depends on all four and converts between them; `harness-tui` and `harness-bridge` depend on core only; the `banana-harness` binary depends on core, tui and bridge. `harness-testkit` is dev infrastructure: it depends on no product crate, is used only as a `dev-dependency`, and stays out of `default-members` so `make setup` never builds it.
- The product name lives only in `harness-core`'s `APP_NAME` / `APP_SLUG`, the binary crate's package name, and the desktop app's package metadata (`gui/package.json` and `gui/electron-builder.yml`: product name, window title, app-data folder name and bundle identifier; ADR 0003); code MUST NOT hardcode it elsewhere.
- Errors use `anyhow::Result` with `.context(...)`; add a `thiserror` enum only where a caller branches on the error. When catching an error and returning another, keep the original as its source.
- Code MUST NOT use `unwrap()` or `expect()` outside tests (the workspace lints deny them); test files opt out with `#![allow(clippy::unwrap_used, clippy::expect_used)]`.
- Tests MUST live in each crate's top-level `tests/` folder and drive the system from the outside: seam 1 is `harness-core`'s surface (open a harness, start turns, read events) against the fake provider owned by `harness-testkit`; seam 2 is the TUI's `App` state rendered with ratatui's `TestBackend`; seam 3 is the sidecar protocol, `harness-bridge`'s `serve` driven over an in-memory stream, plus the real `banana-harness serve --stdio` process; seam 4 is the desktop app through Playwright against a real sidecar and the same scenarios (the app's tests live in `gui/tests/`). Tests MUST NOT be inlined under `src/` or assert on private internals.
- Production code MUST NOT contain test hooks; tests reach the system only through its public surface and the fake provider's `base_url`.
- `harness-bridge` writes only protocol frames to stdout and logs to stderr; its lints deny `print_stdout` and `print_stderr` outside its one `log` helper.
- Dependencies are pinned once in `Cargo.toml` `[workspace.dependencies]` and referenced with `x.workspace = true`; `Cargo.lock` is committed and builds use `--locked`. `rmcp` stays pinned to an exact version. The desktop app's JavaScript dependencies are pinned exactly in `gui/package.json` with a committed `pnpm-lock.yaml` installed with `--frozen-lockfile`, and are all `devDependencies` (they are bundled).
- The API key is read only from `AI_API_KEY`. Keys and other secrets MUST NOT appear in code, config, fixtures, docs or commit messages, and MUST stay redacted from anything persisted, displayed or returned by a tool.
- Every type, config key, helper and table MUST have one canonical owner; code MUST NOT duplicate definitions or add forwarding shims. For example, slash commands live only in `harness-tui`'s `COMMANDS`, which `/help`, the suggestions and dispatch all read; the fake provider lives only in `harness-testkit`; the desktop app's design tokens live only in `gui/src/renderer/styles/tokens.css`.
- A change that makes code unused MUST delete it in the same change: no stale exports, files, docs or "just in case" shims.
- Functions with more than one parameter of the same type MUST take a single options struct instead of repeated positional parameters.
- Database changes go in a new numbered `crates/harness-store/migrations/NNNN.sql` appended to `MIGRATIONS`; a shipped migration MUST NOT be edited.
- Use the domain vocabulary in `CONTEXT.md` (TUI, desktop app, sidecar, headless run, agent, session, turn, interrupted turn, undone turn, thread, required action, provider, workspace, workspace config, restricted mode, workspace trust, guardrail, checkpoint, changes, evaluation issue). A change that introduces or retires a domain term MUST update `CONTEXT.md` in the same change; decisions that are hard to reverse get an ADR in `docs/adr/`.
- User-visible behaviour (key bindings, slash commands, config keys, guardrails) MUST stay in step across the code, `/help` and `README.md`.
- Every nested `AGENTS.md` MUST have a sibling `CLAUDE.md` containing only `@AGENTS.md`, so every coding agent loads the same scoped rules.

## Code comments

- Comments MUST explain intent, trade-offs or constraints and stay brief; they MUST NOT restate the code or include issue-tracker IDs.
- Do NOT add file-level banners that enumerate implementations or call graphs; put a one-line note on the symbol that needs it, or omit it.
- A deliberate simplification with a known ceiling gets a one-line `ponytail:` comment naming the ceiling and the upgrade path.
- TODOs stay to one short line.
